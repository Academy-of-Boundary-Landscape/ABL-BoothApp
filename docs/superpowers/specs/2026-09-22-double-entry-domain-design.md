# ② 领域模型：库存与资金的复式账 设计

**日期**: 2026-09-22
**作者**: Renko_6626（与 Claude 协作）
**状态**: Draft — 排期 v1.2.0（子项目 ②，四个中的第三个执行）
**前置阅读**: `docs/superpowers/specs/2026-09-22-v1.2-roadmap.md`（含 ① 执行后的附录）
**前置任务**: ①（已完成）、③a（handler 类型化）

## 这是什么

v1.2 大修的核心。把「库存」和「资金」从当前的单边扣减改成**移动模型**（每一次变动都有明确的来源和去向），并把折扣从「负价格假商品」改成**一级实体**。

**这不是一个账务系统，是一个单场结算器。** 这个定位贯穿整份设计，是后面绝大多数取舍的依据。

## 定位（最重要的一节）

### 它解决的问题

摊主替社团卖货：钱先到摊主手里，货是社团的，摊位费可能是摊主垫的。展会结束时要回答一个具体问题：

> **我和社团之间，这笔钱怎么结。**

**这是往来结算，不是损益。** 系统不回答"这次赚没赚"，那需要印刷成本、摊位费分摊、跨展会的销售累计——全是这台设备看不全的东西。

### 它不解决的问题，以及为什么

- **每台设备是孤岛。** 社团几个人各装一份，谁出摊谁用自己的，**设备之间不同步**（至多通过 `.boothpack` 同步商品库）。所以任何需要全局视图的功能（总库存、跨展会销售、社团总账）都是做不对的，不做。
- **不做长期收支。** 社团有自己的中心化财务系统。本系统的产出是**导出表格**，导进那边。
- **不记成本、不算毛利。** 这是社团中心财务的事。这台设备只看得见一场展会，算出来的利润必然残缺——**给一个残缺的利润数字比不给更坏**。

### 作用域

**一次展会 = 一个闭环。** 期初带货去，期末结算，中间每一件货都必须能解释去向。

## 1. 骨架：journal + 两张移动表

```
journal            一次业务操作
 ├ stock_movement  货的移动：product_id, from_location, to_location, qty
 └ money_movement  钱的移动：from_account, to_account, amount
```

**每行的 from 和 to 都非空。** 这是移动模型相对经典借贷分录的全部价值：**不存在"不平衡的分录"这种东西**，因为没有"忘了写对手方"这个可能。「借贷必平」从一个需要主动校验的不变量，变成一个写不出来的错误。

取代现状：`products.current_stock` 是唯一真相，**三个互不共享的写入方**（下单扣 `api/order.rs:130`、取消退 `api/order.rs:451`、管理员改初始库存 `api/product.rs:230`，其中第三个还不在事务里）。所有"库存数字不对"的 bug 都是从这个形状长出来的。

### 为什么是两张表而不是一张带 kind 的表

货和钱的列、约束、索引都不同。并成一张只会得到一堆 nullable 列和一个判别符，每次查询都要先过滤 kind。它们靠 `journal_id` 绑在一起，这已经足够。

### 为什么不用「账户 + 商品维度」的经典形态

经典会计里库存记成「账户 = 位置，商品是分录上的一个维度」，一笔分录可以有任意条腿。调研这个领域后，**多腿场景基本不存在**：

| 场景 | 实际形态 |
|---|---|
| 一笔订单卖 5 件不同商品 | 5 行移动共享一个 journal，**不是多腿** |
| 盘点调整 20 个商品 | 20 行移动共享一个 journal |
| 一箱书淋雨，3 本报废 7 本照卖 | 1 行（现场仓 → 损耗） |
| 退货，部分入库部分报废 | 两笔各自 2 腿 |

唯一真正的多腿是「1 变 N 的转换」（拆礼盒），而它被下面第 3 节的判据消解了，且即便发生也能用虚拟位置表达（见 3.2）。

**结论：放弃多腿能力，换来结构性的平衡保证。** 对一个曾经因为缺少约束而反复出错的项目，这笔交换值得。

## 2. 货的位置

```
外部 ──带货去──▶ 现场仓 ──下单──▶ 顾客仓 ──退货──▶ 现场仓
        ◀─带回──┤  ├──赠送──▶ 赠品
                │  ├──报废──▶ 损耗
                │  └──盘点──▶ 差异（反向为盘盈）
                └──拆封──▶ 转换 ──▶ 现场仓
```

| 位置 | 含义 |
|---|---|
| `外部` | **边界账户**，代表社团库存/家里。系统不追踪它的余额 |
| `现场仓` | 这次带到摊位、当前可售的货 |
| `顾客仓` | 已卖出的货 |
| `损耗` | 报废、损坏 |
| `赠品` | 送出去的货（见 4.4） |
| `差异` | 盘点对不上的部分 |
| `转换` | 破坏性组装/拆封的中转（见 3.2） |

### 余额怎么算：实时聚合，不做缓存

**库存余额 = 对移动流水实时聚合。不维护 `current_stock` 缓存字段。**

新模型里**不存在可以漂移的缓存**——余额是流水的函数，没有"两个数字对不上"的可能。

代价是每次读库存都要聚合。摊位规模下不是问题：一场展会几十个商品、几百到几千条移动，加 `(event_id, product_id)` 索引后是微秒级。**若实测慢了再加物化缓存**——但那时它是纯优化，有流水做权威源可随时重算校验，与上一版「缓存就是唯一真相」性质完全不同。

## 3. 商品、归属、包装

### 3.1 归属：货主是同人社团

- **货主的单位是同人社团**，没有"个人"这一档。
- 本机有一个「本社团」设置，**商品默认归属它**，可改成别的社团（帮别的社团卖货的情形）。
- 归属挂在**全局商品库**（`master_products.owner`）——同人志的归属基本等于"谁出的本"，是稳定属性。挂在展会商品上会让每次选品多一步录入，摊主多半随手跳过。
- `.boothpack` 导入导出时归属跟着走。

**结算按货主分组**，每个货主一张结算单。

### 3.2 包装的判据：能不能无损还原

> **能**（5 本书装袋里）→ 它是 **Lot**，纯定价构造，账上永远是 5 件散货，**不产生任何移动**
> **不能**（塑封礼盒，拆了就废）→ 它是**独立 SKU**，进出库按自己算

这条判据的价值在于：Lot 管定价、movement 管实物，这两套机制本来就各自存在，判据把「什么时候用哪套」说死了，不留模糊地带。

破坏性组装用 `转换` 位置表达，两行各自平衡，靠 journal 绑定：

```
journal「礼盒拆封」
  (礼盒SKU, 现场仓 → 转换,   1)
  (本子A,   转换   → 现场仓, 5)
```

跨 SKU 的数量守恒（1 礼盒 = 5 本子）**不被系统保证**——但经典多腿分录同样不保证（它只管数量代数和），所以这不是移动模型的损失。

**不做配方（BOM）。** 系统不预先记住"礼盒 = 1 本子 + 1 明信片"，组装那次由人直接记消耗与产出。这类操作一次展会做一两种、做一次，为它建配方维护界面是过度设计。将来若发现反复组装，加配方是纯增量，不用改模型。

破坏性组装**几乎只发生在展前**，不需要为它优化现场交互。

## 4. 定价：Lot 与折扣

### 4.1 Lot 的定义

```
Lot = 候选商品集合 + 要选几件(N) + 总价
```

| 现场说法 | 表达 |
|---|---|
| 「甲 + 乙 合购 50」 | 候选 = {甲, 乙}，N = 2，价 50 |
| 「全套 5 本 100」 | 候选 = 那 5 本，N = 5，价 100 |
| 「本子任选 3 本 100」 | 候选 = 所有本子，N = 3，价 100 |

**固定成分是「任选 N」的特例**（N = 候选集大小）。模型只有一个概念，不是两套并行——这正是我们一直在避免的形状。

**单品也是 Lot**：候选集只有它自己、N = 1、价格就是单价。但**UI 层完全不露头**——管理员眼里仍然是"改这个商品的价格"，不是"改这个只有一件商品的套装的价格"。

**Lot 的作用域是展会**，和摊位商品的价格同级——因为 Lot 的总价必须和当次定价一致。跨展会复用 Lot 配置不在本范围（设备不同步，没有可靠的复用来源）。

**不做满减、不做买赠。** 满减是金额阈值型，和件数型混在一起时「先套哪条」会影响总价，没有普遍正确的答案，只能靠配置——那就是路线图里已砍掉的促销规则引擎。

### 4.2 最优折扣求解器

**纯函数**：输入购物车 + 可用 Lot 集合，输出「哪几件进哪个 Lot」+ 总价。不碰数据库、不碰网络、不碰 Tauri。

本质是加权集合覆盖。难点在于**它要替顾客挑哪几件进 Lot**：「任选 3 本 100」而购物车里有 30/35/40/45 四本时，放最贵的三本省 20，放最便宜的三本只省 5——**挑错了"最优折扣"就名不副实**。

摊位规模（购物车十几件、Lot 十几个）暴力搜索加记忆化足够，性能不是问题。

**这是整个子项目里最容易写单元测试、也最值得写的一块**——纯函数，输入输出都是普通数据结构。

### 4.3 手工覆盖通道

求解器覆盖不到的情况必须有出口。**主通道是「直接改总价」**——现场最常见的说法就是「这堆算你 150」，摊主心里已经有个数，不会去想该套哪个 Lot。

```
原价合计      190
求解器价      170   ← 自动套用「任选3本100」
手工改成      150
──────────────────
自动折让      -20
手工折让      -20
```

差额自动归入**手工折让分录**，结算单上那一行是自动填的。

辅助通道是「拆/改 Lot 分配」，给精细控制，但预计用得少。

三条约束：

- **货那一侧完全不受影响。** 手工覆盖只动钱，商品该怎么移动还怎么移动。这保证「每件货都有去向」不会被手工操作破坏。
- **全程可审计。** 订单同时记下原价合计、求解器价、手工最终价。
- **覆盖不改 Lot 定义。** 这一单让的价不污染 Lot 配置。

### 4.4 混货主的手工折让：由本社团全额承担

购物车里有社团A的本子 30、社团B的本子 20，摊主说「算你 40」——这 10 块**全部算在本社团头上**。社团B按原价 20 结算。

**不按比例分摊。** 理由：按比例看似公平，但它把"摊主的营销决定"的成本转嫁给一个没有参与决定的人。代卖关系的常识是「我帮你卖货，我自己让的价不该由你买单」。

实际好处：帮卖的社团拿到结算单时，数字和他们自己的定价完全对得上，**不需要理解摊主当天做了什么人情**，减少解释成本和扯皮。

**Lot 折让不适用这条**——Lot 是预先配置的定价规则，参与 Lot 的商品各自按 Lot 价在其成分间按原价比例分摊，跨货主时各自承担自己那份。

### 4.5 订单行必须存「分摊后金额」

每个订单行除了商品和数量，**必须存这一行最终实际承担的金额**（Lot 分摊 + 手工折让分摊之后）。

两个下游都依赖它：

- **按货主结算**：混货主订单要拆到各社团头上
- **退货**：退某一行时，退款金额就是这一行的分摊额

分摊规则：Lot 内部按成分原价比例分摊 Lot 价；手工折让按 4.4 全额记在本社团的行上（本社团有多行时在这些行间按原价比例分摊）。

### 4.6 赠品

- **进了 SKU 的**：走赠品移动（`现场仓 → 赠品`），订单上一条 0 元行
- **没进 SKU 的小东西**（贴纸、糖果）：系统不管。本来就不在库存里，没有可移动的对象，硬记是负担

**预售取货**不需要新机制——开一个 0 元商品即可。

## 5. 钱的账户

| 账户 | 含义 |
|---|---|
| `摊主自有` | **边界**，摊主自己的钱 |
| `实收-现金` / `实收-微信` / `实收-支付宝` / `实收-<自定义>` | 摊主实际持有的各渠道款项。**渠道可自定义**（有社团用银行转账、有的用闲鱼），但至少预置现金/微信/支付宝三种 |
| `社团往来:<社团>` | **结算账户**。余额 = 他们欠我 − 我欠他们 |
| `结算调整` | **边界**，供协商性调整用 |
| `对账差异` | **边界**，收摊核对不上的差额 |

### 5.1 「应收」科目被取消（对 D2 的修正）

路线图 D2 原先定的是「订单完成 = 记应收；摊主确认到账 = 应收 → 渠道账户」两步。

**现场事实否掉了这个模型**：一手交钱一手交货，摊主看到微信到账提示才点完成——**完成订单就是确认收到钱，是一个动作**。「应收」在正常流程里从不留余额，它是两步模型的产物。

**所以取消应收科目。** 应收与实收的差异只在**收摊对账时出现一次**（对着微信/支付宝账单和现金盒核），不是每单一个待确认状态。

### 5.2 三类操作

| 操作 | 移动 | 往来余额 |
|---|---|---|
| 卖出社团A的货 30，微信收 | `社团往来:A → 实收-微信  30` | −30（我欠他们 30） |
| 垫付摊位费 400（记社团A头上） | `摊主自有 → 社团往来:A  400` | +370 |
| 协商赔付丢失的书 20 | `社团往来:A → 结算调整  20` | +350 |
| 收摊：微信账单比账面少 2 | `实收-微信 → 对账差异  2` | 不变 |

**结算单上「我应转给社团A」= 往来余额取负。** 整张结算单是这个账户的余额，不是另外算出来的数字。

### 5.3 垫付支出：自由行，不自动分摊

每条垫付写明 **(社团, 名目, 金额)**，系统**不做任何自动分摊**。两个社团合摊位子就记两条「XX社团摊位费」。

分摊怎么算是社团之间的事，软件只负责把「我垫了多少、算谁头上」记清楚。**不发明分摊规则。**

### 5.4 结算调整：可追加，且入账

每个货主下可追加任意条调整，**有金额和说明，正负皆可**（赔付、减免、上次没结清的尾数…）。

**调整入账本**（记成 `社团往来 → 结算调整` 的移动），不是报表上临时加的一行——它是真实发生的债务变动，事后要查得到。

## 6. 订单与生命周期

### 6.1 下单即移动，取消走冲正

```
现场仓 ──下单──▶ 顾客仓
          ◀──取消（冲正 journal，关联原 journal）──┘
```

**不引入「预留」中间位置。** 现场节奏是几秒内、摊主总能看见下了哪些单，弃单窗口小到不值得为它多建一个位置和一段状态流转。

**冲正而不是删除**，是会计的标准做法，也留下审计痕迹（弃单率随时能查）。

**下单即移动天然防超卖**——货在下单那一刻就离开现场仓了。

### 6.2 完成 = 收钱，一步

订单完成时一次记：`社团往来:<货主> → 实收-<渠道>`，按 4.5 的分摊额拆到各货主。

**结算时必须录收款渠道**，否则钱那条腿没有对手账户。摊主本来就要人工点「确认收款」，把渠道选择并进那一步，不增加操作次数。

### 6.3 退货

按**订单行**退。退款金额 = 该行的分摊额（4.5）。

```
货：  顾客仓 → 现场仓（可售）或 顾客仓 → 损耗（已损坏）
钱：  实收-<渠道> → 社团往来:<货主>
```

### 6.4 展会生命周期

```
筹备 ──开场(带货去)──▶ 进行中 ──收摊(盘点)──▶ 已结算
```

- **开场**：逐个录「这次带多少」，生成 `外部 → 现场仓` 的移动。社团寄货常附货物单，照着录即可。（将来可做货物单导入，不在本范围。）
- **收摊**：盘点生成 `现场仓 → 差异` 或反向的调整移动，然后剩余货 `现场仓 → 外部`（带回）。

**盘点可以跳过，但结算单上会明写「未盘点，剩余数为账面推算」。** 不做硬性阻断——总有意外（展会清场赶人）——但要让跳过留下痕迹而不是悄无声息。

**进入「已结算」之后，账本冻结**：不能再下单、退货、改盘点数。仍然允许的只有**追加结算调整**（5.4）——因为「回家后发现少了一本，和社团协商赔多少」正是展会之后才会发生的事，这也是当初要求调整项可追加的原因。

## 7. 结算单

每个货主一张，外加一张跨货主的收摊对账。

```
━━ 展会结算 ━━  ABC漫展 · 2026-10-01 · 摊主：老王

┌─ 货主：星见社（本社团）────────────────
│ 【货】带去 90 → 卖出 61 / 赠送 4 / 报废 1 / 带回 24   盘点差异 0
│ 【钱】商品原价 1,830  Lot折让 -120  手工折让 -60 → 净额 1,650
│ 【我垫付】摊位费 400 + 打印费 80 = 480
│ 【调整】现金短少 −5（我认）
│ ───────────────────────────────
│ 我应转给星见社：1,170
└─────────────────────────────────

┌─ 货主：黄昏堂（帮卖）─────────────────
│ 【货】带去 30 → 卖出 12 / 带回 18                    盘点差异 0
│ 【钱】商品原价 360  折让 0 → 净额 360
│ 【调整】弄丢 1 本，按成本赔 20
│ ───────────────────────────────
│ 我应转给黄昏堂：380
└─────────────────────────────────

【收摊清点（跨货主）】
  微信账单 1,540 ✓  支付宝 320 ✓  现金盒 145（应 150，短 5）
  实际到手 2,005 ／ 应有 2,010
```

**钱的清点是跨货主的，结算是按货主的。** 现金盒里的钱不分谁的货卖的，所以「对账」（我手上的钱对不对）和「结算」（每个货主该拿多少）是两件事。

**导出是一等公民**，不是附属功能。产出财务表和库存表，导进社团自己的系统。

## 9. 测试策略

① 建立的 `src-tauri/src/test_support.rs` 三个夹具（`test_pool` / `test_state` / `test_router`，内存 SQLite + `tower::oneshot`，不需要 Tauri runtime）把写测试的成本降到接近零。**本子项目必须用满它们。**

最高价值的三个靶子：

1. **折扣求解器**（4.2）——纯函数，输入输出都是普通数据结构。必须覆盖「挑最贵的几件进 Lot」这类容易写错的分配决策。
2. **分摊规则**（4.5、4.4）——混货主 + Lot + 手工折让叠加时，各行分摊额之和必须等于最终总价，且手工折让必须全额落在本社团。这是个不变量，写成断言。
3. **结算单的自洽**——「带去 = 卖出 + 赠送 + 报废 + 带回 + 差异」对每个商品成立；「往来余额 = 销售净额 − 垫付 + 调整」对每个货主成立。这两条是整个模型的核心不变量。

**最终评审已指出：① 之后业务逻辑测试覆盖率实质为零**（43 个 route 只有 2 个有 HTTP 测试）。②**必须先为要改的业务路径补 HTTP 层测试再动逻辑**，不能默认已有保护。

## 10. 明确不做（YAGNI）

| 不做 | 为什么 |
|---|---|
| 成本、毛利、回本进度 | 社团中心财务的事。单设备算出的利润必然残缺 |
| 跨展会连续账 | 设备不同步，做不对 |
| 满减、买赠规则引擎 | 规则优先级没有普遍正确的答案 |
| 自动费用分摊 | 分摊是社团之间的事，不发明规则 |
| 配方（BOM） | 组装一次展会做一两次，过度设计 |
| 多腿分录 | 领域里基本不存在（见 1） |
| 应收科目 | 现场是一步操作（见 5.1） |
| 「预留」位置 | 弃单窗口只有几秒（见 6.1） |
| 个人作为货主 | 一切以同人社团为单位 |

---

## 11. 不能破坏的

1. **离线局域网。** 任何新特性一旦要求联网前提，都会反噬产品最核心的信任基础。
2. **支付非闭环的诚实披露。** `docs/guide/workflow.md` 那句「'订单已完成' 仅代表记录了一笔账，不代表钱真的到了你的账户」在复式记账引入后**依然成立且更需要强调**——「完成订单」是记账动作，不是收款动作。**不得让复式记账制造出「钱已到账」的错觉。**
3. **签名材料的连续性**（`my-release-key.jks`、`src-tauri/updater-key.key`）。

## 附：schema 草图

不是最终 DDL（那是实现计划的事），但把上面的设计落成表，是检验它自洽与否的最快方式。

```sql
-- 商品库（全局，跨展会）
master_products(id, product_code UNIQUE, name, owner_society, default_price, ...)

-- 展会
events(id, name, event_date, status /* 筹备|进行中|已结算 */, ...)

-- 摊位商品：这次展会带了哪些货、卖多少钱
--   注意：没有 current_stock —— 余额从 stock_movement 聚合
event_products(id, event_id, master_product_id, unit_price, UNIQUE(event_id, master_product_id))

-- Lot：候选集 + 选 N 件 + 总价，作用域是展会
lots(id, event_id, name, pick_count, total_price)
lot_candidates(lot_id, event_product_id)

-- 一次业务操作
journals(id, event_id, kind /* 带货去|销售|退货|赠送|报废|盘点|带回|拆封|垫付|调整 */,
         occurred_at, reverses_journal_id /* 冲正时指向原 journal */, note)

-- 货的移动：from/to 均非空 ⇒ 结构上不可能不平衡
stock_movements(id, journal_id, event_product_id, from_location, to_location, qty CHECK(qty > 0))

-- 钱的移动：同上
money_movements(id, journal_id, from_account, to_account, amount CHECK(amount > 0))

-- 订单（销售 journal 的业务视图）
orders(id, journal_id, event_id, status, channel /* 现金|微信|... */,
       gross_amount    /* 原价合计 */,
       solved_amount   /* 求解器给的价 */,
       final_amount    /* 手工覆盖后的最终价，无覆盖时等于 solved */)

-- 订单行：allocated_amount 是 4.5 的分摊额，退货和按货主结算都靠它
order_lines(id, order_id, event_product_id, qty, unit_price,
            lot_id /* 进了哪个 Lot，NULL 表示未参与 */,
            allocated_amount)

-- 垫付：自由行，每条写明算谁头上
advances(id, event_id, owner_society, label, amount)

-- 结算调整：可在已结算之后追加
settlement_adjustments(id, event_id, owner_society, label, amount /* 可正可负 */, journal_id)
```

几个值得指出的形状：

- **`event_products` 没有 `current_stock`。** 这是整个设计最直接的体现——可售余额是
  `SUM(到现场仓) − SUM(离现场仓)`，不存在第二个可以漂移的数字。
- **`journals.reverses_journal_id`** 让冲正可追溯，取消订单不删数据。
- **`order_lines.allocated_amount`** 是 4.4 / 4.5 全部分摊规则的落点。
  不变量：同一订单所有行的 `allocated_amount` 之和 = `orders.final_amount`。
- **`money_movements` 不带 `owner_society` 字段**——货主信息在 `社团往来:<社团>` 这个账户名里。
  账户用字符串而不是外键，因为 `实收-微信`、`摊主自有` 这些不挂任何社团。
