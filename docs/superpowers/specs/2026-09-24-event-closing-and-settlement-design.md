## 这是什么

②-1 建了账本骨架，②-2 建了定价与折扣。**货能进来、能卖出去，但出不去。**

现在展会没有终点：pending 订单可以永远挂着，卖剩的货没有地方去，摊主和社团之间那笔钱算不出来，退货完全没有入口。②-3 把这一圈合上。

母 spec 第 6.4 节和第 7 节已经把语义定了，本文不重复，只写**它们没说而实现必须回答的部分**，以及三处对母 spec 的有意偏离。

## 对母 spec 的三处有意偏离

**都是 2026-09-24 brainstorm 里逐条确认的，不是遗漏。**

### 偏离 1 — 赠品不是订单行（推翻 4.6）

母 spec 4.6 写「订单上一条 0 元行」。本文改成**独立登记**，和报废共用一套入口。

理由：做成订单行要让求解器、`allocate_lot`、`apply_manual_adjustment`、`order_lots` 全部容忍 0 元行，而**收益是零**——结算单第 7 节那行「卖出 61 / 赠送 4 / 报废 1 / 带回 24」本来就是从 `stock_movements` 按位置汇总的，不需要赠品挂在订单上。「买二送一」该用 Lot 表达（D4），不该用赠品表达。误登记走 `reverse_journal()` 撤销，比退货通道轻得多。

**连带作废**：母 spec 6.3 末段「赠品行的货在 `赠品` 而不是 `顾客仓`，退回时从记录的目标位置反向」——订单行的货此后恒在顾客仓，退货的货腿起点是常量。

### 偏离 2 — 赠品默认零资金腿，「摊主自掏」是可选开关

母 spec 4.6 没说赠品的钱怎么记。本文定：**默认只有货腿**（`现场仓 → 赠品`），货主自己承担。摊主勾「这笔我自掏」才追加一条资金腿：

```
社团往来:<货主> → 摊主自有      unit_price × qty
```

**方向和一次销售完全同形**，只是把 `实收-<渠道>` 换成了 `摊主自有`——摊主把自己当成顾客，用自己的钱「买」下这件货再送出去。所以往来余额 −price（我欠货主 price），而「我应转给货主 = 往来余额取负」自动 +price。

反过来写（`摊主自有 → 社团往来`）是**垫付**的方向，意思变成「货主欠我 price」，正好错一个符号，而且账面仍然平、测不出来——只有对着结算单上「我应转给」那个数才看得出。这条初稿写反过，2026-09-24 核账时抓出来。

默认零腿是因为绝大多数赠品是送自家货，记一笔「摊主个人买下自家社团的货」只会让单人摊主看不懂结算单。但代卖那条不能完全不管——送掉代卖社团的货，货主一分拿不到——所以留这个开关，并在结算单上**按货主分列赠送数**，让摊主看见并自己决定要不要补一条结算调整。**不发明分摊规则**，和 5.3 对垫付的态度一致。

### 偏离 3 — 冻结后还允许两件事：收摊清点、追加垫付

母 spec 6.4 写「进入已结算之后……仍然允许的只有追加结算调整」。本文放宽成三件：

| 冻结后允许 | 为什么 |
|---|---|
| 追加结算调整 | 母 spec 原有 |
| **跨货主的收摊清点** | 对账差异默认摊主自吞（母 spec 第 5 节），**不进任何货主的结算**，只影响「摊主留存」那一个数。而回家才有空数现金盒、对微信账单是常态 |
| **追加垫付** | 「回家翻出一张打印费收据」和「回家发现少了一本书」是同一类事件，母 spec 允许后者却禁止前者说不通 |

**垫付放开是 2026-09-24 评审时明确要求的**，推翻了本文初稿里「走结算调整补」那个方案。初稿的理由是「不让已经交给社团的结算单事后变数」，但那个担心对结算调整同样成立，而母 spec 本来就接受了——收摊之后账还会动，正是结算调整存在的全部理由。逼着摊主把一笔真实的垫付伪装成「调整」，只会让结算单上的两栏都失真。

想把对账差异推给某个货主，仍然只能追加结算调整——**「对账」和「结算」是两件事**这条不破。

## 1. 收摊向导

### 1.1 一个只读端点决定每一步

```
GET /events/:id/closing
→ {
    status: "进行中",
    pending_orders: [{ id, created_at, final_amount, lines: [...] }],
    onsite_remaining: [{ event_product_id, product_code, name,
                         owner_society_id, owner_name, qty }],
    stocktaken_at: null,
    blockers: ["还有 3 单待处理，清完才能盘点"]
  }
```

**前端不自己判断能不能进下一步**，`blockers` 空了才放行。理由和 ②-2 把试算放后端一样：判据写在两处就会有一处先腐烂。

### 1.2 第 ① 步：清 pending（硬阻断）

列出全部 pending，逐单「完成（补录渠道）」或「取消」。

**一键全部取消走前端循环调用现有 `PUT /events/:id/orders/:oid/status`，不新开批量端点。** 每单取消本来就该是独立事务——一单因为并发失败，不该把已经取消成功的那几单一起回滚。界面按单显示结果，失败的留在列表里。

硬阻断的理由是母 spec 写明的：pending 订单的货已经在顾客仓、钱一分没收，留着它们，第 9 节的「顾客仓余额 = 卖出」就不成立。

### 1.3 第 ② 步：盘点（可跳过）

`POST /events/:id/closing/stocktake`

```json
{ "counts": [ { "event_product_id": 12, "counted_qty": 7 }, ... ] }
```

**收全量**——现场仓余额非 0 的商品全部要出现在请求里，数过一致的也传。「我数了，一致」和「我没数这个」是两件事，请求体不该把它们混成同一个缺省。

后端只为有差异的写腿，一条 `Stocktake` journal 带 N 条 `stock_movements`：

- 实数 < 账面：`现场仓 → 差异`，qty = 账面 − 实数
- 实数 > 账面：`差异 → 现场仓`，qty = 实数 − 账面

**只动货，不动钱。** 盘亏的赔付是摊主和社团协商的结果，走结算调整（5.4），不是系统能推出来的。

无论有没有差异，成功后写 `events.stocktaken_at = CURRENT_TIMESTAMP`（见 2.1）。

盘点在向导里只做一次。做完之后如果又卖了一件（理论上 pending 已清、但摊主可能又开单），账面数会变，而 `stocktaken_at` 不回滚——结算单上「盘点于 X 时」是一个时间点的事实，不声称之后没再动过。

### 1.4 第 ③ 步：带回（一键）

`POST /events/:id/closing/takeback`，无请求体。所有现场仓余额 > 0 的商品 `现场仓 → 外部`，一条 `TakeBack` journal。

**不逐个录数**——账面数就是答案。摊主要改的是盘点那一步该改的东西，不是这里。

### 1.5 第 ④ 步：转已结算

`POST /events/:id/closing/settle`。检查两条：

1. 无 pending 订单
2. 每个商品的现场仓余额为 0

通过则 `events.status = '已结算'`。**盘点没做也放行**，但结算单上明写「未盘点，剩余数为账面推算」——总有意外（展会清场赶人），要让跳过留下痕迹而不是变成硬门槛。

### 1.6 可中断

四步之间没有会话状态。每一步的成果都是已落库的 journal，向导只是按 `GET .../closing` 的返回决定给你看哪一屏。退出、换设备、重进，都从当前真实状态继续。

## 2. Schema 变更

### 2.1 唯一的一条新迁移

```sql
-- 202609240002_add_stocktaken_at.sql
ALTER TABLE events ADD COLUMN stocktaken_at DATETIME;
```

**为什么需要它**：「盘了一遍，全对」和「根本没盘」必须分得开，否则 1.5 那句标注是瞎写。而零差异盘点写不出 journal——`post_journal()` 拒绝空腿，②-1 的原话是「记空 journal 会造出『造得出却冲不掉』的幽灵 journal」。反查 `journals WHERE kind='盘点'` 的存在性只能覆盖「有差异」那一半。

结算单也正好要这个时间戳来打印「盘点于 10-01 18:23」。

**`refunds` / `advances` / `settlement_adjustments` 三张表在 ②-1 就建好了，本轮只往里写数据，一个字段都不加。** 母 spec 附录的 schema 草图是权威。

### 2.2 发布前必查

`docs/BUILD.md` 的「发布前必查」照常适用：**不得改动任何已被应用过的迁移文件**，新增文件没问题。本轮只新增一个。

## 3. 冻结守卫

### 3.1 判据是「不是已结算」，不是「必须进行中」

这一条最容易写反。筹备阶段本来就要能选品、改价、录带货数。

```rust
// api/guard.rs
pub async fn require_event_open(pool: &SqlitePool, event_id: i64) -> ApiResult<()>
// 状态为 '已结算' 时返回 409 Conflict：「已结算的展会不能再改账」
```

| 写入口 | 要求 | 出处 |
|---|---|---|
| `create_order` | **必须 `进行中`** | ②-1 Task 7 已有，不动 |
| `update_order_status`（完成 / 取消） | ≠ 已结算 | ②-1 交接列的敞口 |
| `add_product_to_event` | ≠ 已结算 | 同上 |
| `restock_product` | ≠ 已结算 | 同上 |
| `update_product` | ≠ 已结算 | 同上 |
| Lot 的四个写入口（含 `/quote`） | 已查（②-2 Task 4） | 对齐成调用同一个函数 |
| 赠送 / 报废 / 撤销 | ≠ 已结算 | 本轮新增 |
| 退货 | ≠ 已结算 | 本轮新增 |
| 盘点 / 带回 / 转已结算 | ≠ 已结算 | 本轮新增 |
| **垫付（增删）** | **任何状态** | 偏离 3 |
| **结算调整（增删）** | **任何状态** | 母 spec 6.4 的例外 |
| **收摊清点** | **任何状态** | 偏离 3 |

### 3.2 冻结后仍然能写的三个东西

垫付、结算调整、收摊清点（偏离 3）。**这三个都不调用 `require_event_open`**，而且要各自有一条「已结算展会上仍然成功」的测试——否则后面的人看见其余端点都守着，会顺手把守卫补上去，把有意的例外当成漏掉的。

代价是结算单会在冻结之后继续变。这是接受的：母 spec 6.4 允许追加结算调整时就已经接受了，本文只是把垫付和它拉平。**结算单页面因此要显示「最后更新于」**，让摊主知道手里那张导出的表是不是最新的。

### 3.3 CI 门禁

`api/` 下每个非 GET handler 要么调用 `require_event_open`（或那条更严的 `进行中` 检查），要么带一行 `// 不需要展会守卫：<理由>` 注释。脚本扫描 + `.github/workflows/ci.yml` 接入。

**靠记不住。** ②-1 列出 4 个敞口，②-2 一个没补，本轮还要再加十来个写入口——这已经被证伪两轮了。

## 4. 赠送与报废

```
报废   Scrap journal   货：现场仓 → 损耗      钱：无
赠送   Gift  journal   货：现场仓 → 赠品      钱：默认无
```

```
POST /events/:id/gifts    { event_product_id, qty, note, vendor_pays: false }
POST /events/:id/scraps   { event_product_id, qty, note }
GET  /events/:id/gifts    /  GET /events/:id/scraps
POST /events/:id/journals/:jid/reverse
```

`vendor_pays: true` 时追加一条 `社团往来:<货主> → 摊主自有`，金额 `unit_price × qty`（**方向见偏离 2，别写成垫付那个方向**）。`unit_price` 取 `event_products.unit_price`（展会内的快照价，不是 `master_products.default_price`）。

数量不得超过当前现场仓余额，超了 400。

**撤销走 `reverse_journal()`，不做编辑。** 撤销端点只接受本展会的、kind 为 `赠送` 或 `报废` 的 journal——不能拿它去冲销售或收款，那两个各有自己的通道。`journals` 上的偏索引保证一条 journal 只能被冲正一次。

## 5. 退货

### 5.1 入口与粒度

摊主端「已完成订单」列表里一单一个「退货」。**按 `order_lines` 逐行退，不合并显示。**

交接契约 #3 的原话：「要么允许两行分别退，要么在界面上合并显示、在写入时按行分配。前者更简单也更诚实。」同一个商品因为 Lot 归属拆成两行时，摊主看到的是「本子A（任选3本100）1 件 / 本子A（原价）2 件」，退哪一行是他的决定。

每行可退 `0 ~ (qty − 已退)`。累计退货量超过原 `qty` 返回 400。去向二选一：`现场仓`（还能卖）/ `损耗`（已损坏）。

**只有 `completed` 的订单能退。** `pending` 的直接取消（冲正），`cancelled` 的没有可退的东西——两种都返回 400 并说明该走哪条路。

退货可以发生在收摊向导已经走到带回之后（展会还没转「已结算」）。退到现场仓会让该商品余额重新不为 0，于是 1.5 的检查挡住 `settle`，摊主被迫再走一次带回。**这是对的**，不是 bug：货真的又回到摊位上了。

`POST /events/:id/orders/:oid/refunds`

```json
{
  "channel": "现金",
  "refund_amount": 2000,
  "lines": [ { "order_line_id": 88, "qty": 1, "destination": "现场仓" } ]
}
```

一次请求 = 一条 `Refund` journal + N 行 `refunds`。

### 5.2 两个金额都要用

被退部分的 `allocated` 和 `paid` 按 `qty` 等比切出，**复用 `domain/allocation.rs` 的 `allocate()`**（带 cap 的逐分派发），不另写一份取整规则。

界面上只给摊主**一个**「实际退款」总额，默认 `Σ 各行切出的 paid`。摊主改了就按各行 `paid` 权重摊回每行的 `refund_amount`，各自上限是自己的 `paid`（`CHECK (refund_amount <= paid_amount)` 在 DB 层兜底）。**退多于实付不允许**——那是白送钱，走结算调整。

### 5.3 三条钱腿

设被退部分该行货主应得 `A`（allocated）、顾客实付 `P`（paid）、实际退给顾客 `R`：

```
实收-<退款渠道> → 社团往来:<货主>      A          冲销货主的销售
社团往来:本社团 → 实收-<退款渠道>      A − P      冲销本社团那份手工折让
社团往来:<货主> → 实收-<退款渠道>      P − R      顾客没拿回的部分归货主
```

- 第二条：`A < P`（原单是加价）时方向反过来，金额取绝对值。`A == P` 时无此条。
- 第三条：`R == P` 时无此条。
- 金额恒为正，方向由 `from`/`to` 表达——`post_journal` 对非正金额直接 400（②-1 交接段第 2 条踩过这个坑）。

净流出恰好 `R`。

**覆盖差额（第三条）归货主而不是本社团**，因为它本质上是「剩下的货重新按原价算」，那是货主的货。母 spec 4.5 点名这是「早先版本的一个真漏洞」。

### 5.4 退款渠道

默认等于 `orders.channel`，可改。微信收、现金退很常见，`实收-<渠道>` 那条腿必须是**实际退出去的**那个渠道，否则收摊清点对不上。

退款渠道同样走第 7 节的规范化与历史列表。

### 5.5 不做「退货的同时拆套装」

交接契约 #4 提过这个可能性。不做。

母 spec 6.3 已经给了答案：「任选 3 本 100」退 1 本，按分摊该退 33，但剩下两本原价 80——摊主直接把 R 改成 20。手工改 R 这条通道已经能表达任何结果，而拆套装要在退货里重跑一遍「先拆后摊」的顺序，复杂度不成比例。

## 6. 垫付与结算调整

### 6.1 垫付

`(社团, 名目, 金额)`，**系统不做任何自动分摊**。两个社团合摊位子就记两条「XX社团摊位费」。分摊怎么算是社团之间的事。

每条一个 `Advance` journal：`摊主自有 → 社团往来:<社团>`。

删除走 `reverse_journal()` 冲正 + 删 `advances` 行。列表保持干净，账本留下「一条垫付 + 一条冲正」的痕迹，而「结算单 = 往来账户余额」这条不变量自动成立。

**已结算的展会上仍然可以增删垫付**（偏离 3）。入口和结算调整并排放在管理端结算单页面上。

### 6.2 结算调整

同形，但 `amount` 带符号（`CHECK (amount <> 0)` 已在表上）。

**界面不给摊主填正负号**，给两个方向的按钮：

| 摊主看到的 | 记成 | `社团往来` 余额 |
|---|---|---|
| 我要多给他们 ¥20 | `社团往来:<社团> → 结算调整` | −20 |
| 他们要多给我 ¥20 | `结算调整 → 社团往来:<社团>` | +20 |

让人在收摊后的疲惫状态下判断「赔付该填正还是负」是设计失误。母 spec 5.2 那个例子自己都要算一遍才对得上方向。

**这是冻结后唯一允许的常规写操作**（另一个例外是收摊清点，见偏离 3），所以入口在管理端结算单页面上，且在已结算的展会上仍然可用。

## 7. 自定义渠道

`GET /channels`（**全局，不按展会过滤**）：

```sql
SELECT DISTINCT channel FROM orders  WHERE channel IS NOT NULL
UNION
SELECT DISTINCT channel FROM refunds
```

结果与预置的 `现金` / `微信` / `支付宝` 合并去重返回。跨展会才有意义——上一场用过「银行转账」，这一场当然还想用。

**挂载在 `/api/channels`，不在 `/api/events/:id` 下面**——本轮其余端点都带展会前缀，只有这一个不带，因为它按定义就是跨展会的。

交接契约 #8 的三件套全做：

1. 写库前规范化：`trim` + 内部连续空白折叠为单个空格
2. 长度上限 **20 字符**（按 `chars().count()`，不是字节）
3. 前端是**可输入的下拉**，不是纯文本框

第 3 条才是真正防「微信」和「微信支付」分裂成两个账户的那一条。

**不加白名单**——母 spec 第 5 节明写「渠道可自定义（有社团用银行转账、有的用闲鱼）」。

规范化后为空串则 400。

## 8. 结算单与导出

### 8.1 `domain/settlement.rs` 是纯函数

```rust
pub fn build_report(input: &SettlementInput) -> SettlementReport
```

`SettlementInput` 是一组已经查好的行：货物流水（按「货主 × 商品 × 位置 × 方向」聚合）、订单行金额、垫付、调整、各渠道账户余额、各社团往来余额、`stocktaken_at`。

`SettlementReport` 带一个 `generated_at` 和一个 `last_changed_at`（本展会最新一条 journal 的 `occurred_at`）——冻结之后垫付、调整、清点仍然会动账（偏离 3），摊主得能看出手里的表是不是最新的。

**没有 `async`，不 import `sqlx`。** `api/settlement.rs` 负责查询并喂进去，页面 JSON 和 `settlement.xlsx` 渲染的是**同一个 `SettlementReport`**。这是「页面显示 1,170、导出写 1,150」在结构上不可能发生的唯一办法，也是本轮最高价值的测试靶子——和 ②-2 的求解器地位相同。

### 8.2 每个货主一块

**【货】** 全部从 `stock_movements` 按方向取，不从任何缓存字段取：

| 项 | 来源 |
|---|---|
| 带去 | `from=外部 → to=现场仓` 的 qty 和（开场 + 中途补货，是同一件事） |
| 卖出 | `顾客仓` 的净余额（退货自动减回去） |
| 赠送 | `赠品` 的净余额 |
| 报废 | `损耗` 的净余额（含退到损耗的） |
| 带回 | `from=现场仓 → to=外部` 的 qty 和 |
| 盘点差异 | `差异` 的净余额 |

**恒等式：`带去 − 带回 = 卖出 + 赠送 + 报废 + 差异`。** 这就是货那一侧的借贷必平，等价于「现场仓余额为 0」。`build_report` 直接断言，不平就在报表上显眼标出，不静默出个错数。

`stocktaken_at` 为空时这一块标「未盘点，剩余数为账面推算」。

**【钱】**

```
商品原价  Σ (unit_price × qty)
Lot 折让  Σ (unit_price × qty − allocated_amount)
手工折让  只可能落在本社团（母 spec 4.4），其余货主恒为 0
净额      Σ allocated_amount − 手工折让
```

**每个货主的销售额用 `allocated_amount`，不是 `paid_amount`。** 交接契约 #1 的原话：货主该得多少不受摊主当天做了什么人情的影响。仪表盘用 `paid_amount` 是另一个口径，两者在同一场展会里合法地对不上，差额恰好是手工折让。

**但「净额」这一行要把手工折让减掉**，而且只对本社团减——母 spec 4.4 定了混货主的手工折让由本社团全额承担，母 spec 第 7 节的样例也是这么算的（星见社：原价 1,830 − Lot 折让 120 − 手工折让 60 = 1,650）。代卖货主的净额恒等于 `Σ allocated`。

写成 `净额 = Σ allocated` 会让本社团的结算单多出手工折让那一笔，而账本余额是对的——于是页面上的加减和「我应转给」对不上。初稿漏了这一项，2026-09-24 核账时抓出来。

退货按 `allocated` 冲减。

**【我垫付】/【调整】** 逐条列名目与金额。

**【我应转给 X】= `社团往来:<X>` 的余额取负。** 不是另外加出来的数——这正是「所有影响往来的东西都必须在账本里」（垫付、调整都带 `journal_id`）的全部理由。`build_report` 把上面各项加出来的数和账户余额对一遍，对不上报警。

### 8.3 跨货主的收摊清点

各渠道账面应有 = `实收-<渠道>` 的余额。摊主录实际到手数（微信账单、现金盒），差额写一条 `实收-<渠道> → 对账差异`（账面多于实际）或反向。

```
POST /events/:id/settlement/reconcile
{ "counts": [ { "channel": "现金", "actual": 14500 } ] }
```

允许在已结算之后进行（偏离 3）。允许重复录——每次按「上次清点后的差额」再写一条，不是覆盖。

**摊主留存 = 实际到手合计 − Σ 我应转给各货主。**

差异**不进任何货主的结算**，只出现在清点栏。想推给某个货主，追加一条结算调整。

### 8.4 导出

`GET /events/:id/settlement.xlsx`，沿用现有的 `rust_xlsxwriter`，四个 sheet：

| sheet | 内容 |
|---|---|
| 结算汇总 | 每货主一行（净额 / 垫付 / 调整 / 我应转给）+ 收摊清点栏 |
| 货主明细 | 按商品：带去 / 卖出 / 赠送 / 报废 / 差异 / 带回 + 原价 / 折让 / 净额 |
| 账本流水 | 全部 journal 逐条，带货腿与钱腿 |
| 订单明细 | 逐单逐行，含 `allocated` 与 `paid` 两个金额 |

**老的 `GET /events/:id/sales_summary/download` 保留不动。** 它回答「卖了什么」，这个回答「账怎么算」，受众不同。

## 10. 测试策略

夹具 `test_support.rs` 的 `test_pool()` / `test_state()` / `test_router()` 已备好，HTTP 层集成测试成本接近零。①/②-2 的规矩照旧：**先为要改的业务路径补测试，再动逻辑。**

按价值排的靶子：

1. **`domain/settlement.rs` 的纯函数。** 混货主 + Lot 折让 + 手工折让 + 垫付 + 调整 + 部分退货全叠在一起，断言每个货主的「我应转给」等于 `社团往来` 账户余额。
2. **退货的三条腿。** 混货主 + 折让 + 部分退 + 改 R，四个条件同时成立时的各账户余额。这是母 spec 点名的历史漏洞所在。
3. **冻结守卫逐个写入口。** ②-1 的原话「冻结不能只测下单」——每个非 GET 端点都要有一条「已结算展会上返回 409」。
4. **收摊闭环的不变量。** 走完四步后，每个商品现场仓余额为 0，且全部资金账户余额之和为 0（复式账的总闭合）。
5. **盘点跳过与否的两条路径。** `stocktaken_at` 有无，结算单标注跟着变。
6. **赠送/报废的撤销。** 撤销后位置余额回到原样；同一条 journal 不能撤两次。

顺带补上 ②-2 留下的三条 deferred minor：全代卖订单**加价**的镜像场景、事件级「pending + completed + cancelled 混合时 Σpaid == Σfinal」、`/quote` 的 `MAX_STATE_SPACE` / `MAX_STEPS` 的 HTTP 层测试。

前端：收摊向导的步骤推进逻辑与退货金额摊回是纯函数，走 vitest。**组件与 store 仍然没有测试**，这条从 ②-2 一路留下来，本轮不解决（归 ③b/④）。

## 11. 明确不做（YAGNI）

- **拆封 / 转换**（`Location::Conversion`、`JournalKind::Convert`）。等真实场景出现。
- **退货的同时拆套装**（5.5）。
- **盘点在展会进行中随时可做。** 只在收摊向导里盘一次。中午盘一遍的需求还没出现过。
- **自动分摊垫付。** 母 spec 5.3 明写「不发明分摊规则」。
- **赠品的多档承担比例**（比如「各承担一半」）。只有开关，没有滑块。
- **对账差异的自动归属推断。** 差额默认摊主自吞，想推给谁靠人手工加结算调整。
- **退货的撤销。** 赠送/报废可以整条冲正（第 4 节），退货不行——退货已经涉及三条钱腿和顾客手里的现金，误操作要靠**再开一张相反方向的单**来纠正，而不是让账本上凭空少一笔。真退错了，走结算调整。
- **多设备同步、跨展会累计、成本与毛利。** 母 spec 定位一节已经封死。

## 12. 不能破坏的

1. **离线局域网这条核心链路。** 本轮新增的端点全部走同一个 Axum server，不引入任何外部依赖。
2. **签名材料的连续性。** 不碰 `my-release-key.jks` 与 `src-tauri/updater-key.key`。
3. **支付非闭环的诚实披露。** 结算单上的「我应转给 X」是**账本算出来的应转数**，不是「已经转过」。收摊清点栏的「实际到手」是**摊主自己录的数**，不是系统验证的到账。`docs/guide/workflow.md` 顶部那句黑体在结算单落地后更需要强调——**不得让结算单制造出「钱已经结清」的错觉。**
4. **已发布的迁移文件永久冻结。** 本轮只新增 `202609240002_add_stocktaken_at.sql` 一个文件。
5. **`domain/solver.rs` 与 `domain/allocation.rs` 的签名。** 交接契约的第一句话。退货复用 `allocate()` 是调用，不是修改。
