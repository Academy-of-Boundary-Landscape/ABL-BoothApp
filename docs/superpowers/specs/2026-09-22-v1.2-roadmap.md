## 背景

v1.1.1 发布于 2026-05-01，此后 5 个月无面向用户的改动。2026-09-22 落了四个构建基建提交
（Android 源码入库、构建脚本化并迁到 Linux 开发机、Tauri 工具链对齐 2.11、sqlx 0.7→0.9 清漏洞），
为本次大修铺路。

调研（2026-09-22，四路并行只读扫描）后，确认四个方向的问题都真实存在，且**病根高度一致**：

| 领域 | 已经做了 | 停在哪 |
|---|---|---|
| TypeScript | `typescript` / `vue-tsc` / `@vue/tsconfig` / `@types/node` 全在 devDependencies | **没有 `tsconfig.json`** |
| Lint / 格式化 | eslint / prettier / eslint-plugin-vue 全装 | **没有任何配置文件**；ESLint 9 flat config 缺失等于未启用 |
| E2E | `@playwright/test` 已装 | **没有 `playwright.config.*`**，零测试文件 |
| 设计系统 | `frontend/src/config/theme.js` 424 行真 token 系统（明暗双色板、spacing/radius/font/shadow 四级刻度、`colord` 派生色、`themeStore` 运行时注入 CSS 变量），业务代码 1119 处 `var()` | **没有基于 token 的组件层**，每页手抄一遍 scoped CSS |
| DB 迁移 | `sqlx::migrate!()` 机制齐全，5 个时间戳迁移，启动自动跑 | **只做过加列/加表/加索引**，破坏性变更与回滚路径从未验证 |
| CI | 有 GitHub Actions | `.github/workflows/deploy-docs.yml` **只管 vitepress 文档站**，不碰 `src-tauri/` 和 `frontend/` |
| 测试 | 有一个 `frontend/src/utils/dateFormatter.test.js` | **是 `console.log("✓ 通过")` 脚本**，无断言框架、无退出码、未接入任何 npm script |

**结论：这个项目不是没规划，是每件事都想到一半停了。** 因此 1.2 的相当一部分工作量是"接线"而非"从零建"。

### 架构澄清（影响后续所有判断）

这不是典型的 Tauri IPC 应用。`src-tauri/src/lib.rs:16` 里只有**一个** `#[tauri::command]`
（`get_backend_url`，仅用于把后端地址告诉前端），`frontend/src` 里 `invoke(` **零命中**。
真正的业务是一个跑在 Tauri 进程内的 **Axum HTTP/HTTPS server**（`src-tauri/src/server.rs`，
`127.0.0.1:5140` 回环 + `0.0.0.0:5141` HTTPS 供 LAN），共 48 个 route（vision 关闭时 32 个），前端用 axios 调用。

两个直接后果：

1. **可测性比想象中好**：业务逻辑可脱离 Tauri runtime，用内存 SQLite + `tower::ServiceExt::oneshot`
   做 handler 级集成测试，无需开窗口。sqlx 用运行时 `migrate!()` 而非编译期 `query!` 宏，
   连 `DATABASE_URL` 都不需要。
2. **契约是真 Web API 而非 IPC**，因此 OpenAPI 这条路是通的。

## 分解

四个子项目，各自一份 spec + plan：

### ① 安全网

CI gate、测试脚手架、lint/format 接线、数据备份保险丝、零风险清扫。
**最便宜**（依赖全装好了，只差配置文件），且是后三者的前提。

### ② 领域模型

完整复式记账（货 + 钱）、统一 Lot 售卖单元、最优折扣求解器、折让/赠品/损耗/盘点、全新 schema。
**最重、风险最高**，安排在 ① 之后以便有测试保护。

### ③ 契约与 TypeScript

拆成两段，中间隔着 ②：

- **③a** — 48 个 route（vision 关闭时 32 个） 的响应与错误收口成具名类型。是 ② 和 ③b 的**共同前提**，跑不掉。
- **③b** — utoipa 注解 → `openapi.json` → 生成 TS client；前端全量 TS 迁移。
  必须等 ② 定型，否则生成完就作废。

### ④ 外观

组件层收口、信息架构重设计、移动端改善。**视觉方向不动。**

一份 spec，但内部分两批实现：「组件层收口」与「移动端」不依赖 ②，可从 ① 之后并行开工；
「IA 重设计」必须等 ② 定型（理由见下节）。

## 执行顺序

依赖关系逼出来的，不是偏好：

```
① 安全网
    ↓
③a handler 类型化 + 错误统一      ← ② 和 ③b 的共同前提
    ↓
② 领域模型
    ↓
③b utoipa + TS client + 前端 TS 全量迁移
    ↓
④ IA 重设计

    ④ 的「组件层收口」与「移动端」可从 ① 之后并行开工
```

**两条关键依赖，容易被忽略：**

1. **③a 必须在 ② 之前。** 现在 route handler 返回的是 `(StatusCode, Json(json!({"error": ...})))` 这种
   宏拼出来的匿名 JSON，根本没有类型（`thiserror` 在 `Cargo.toml` 里但全仓只有 `src-tauri/src/utils/cert.rs:27`
   用了一处，`anyhow` 零使用）。不先收口，② 的新领域概念会继续以无类型 JSON 的形式漏出去。

2. **④ 的 IA 重设计不能和 ② 并行。** ② 会引入一批现在不存在的用户概念——套装管理、盘点登记、
   损耗/赠品、收款渠道对账——这些都需要在导航和页面职责里有位置。先重设计 IA 再塞进去，等于改两遍。

## 分支与发布策略

`1.2-dev` 长命分支，四个子项目顺序合入。每个子项目完成时打 `v1.2.0-beta.N`，
在**真 Windows 和真手机**上验证后再进入下一个子项目。最后合 main 发 `v1.2.0`。

真机验证不可省略：交叉编译只证明编得过、打得出包。COM / DXGI / WebView2 / 摄像头 / NNAPI
的运行时行为，以及 NSIS 安装卸载、updater 签名校验、局域网多设备联调，CI 全部覆盖不到。

分支存活期内 main 只接受紧急修复。

## 跨子项目决策

以下决策已确认，四份子 spec 均以此为前提，不再重新讨论。

### D1 — 历史数据：知情清零

老用户本地 `sale_system.db` 的展会、订单、`order_items`、当前库存**不迁移**到新模型。
商品库通过现有 `.boothpack` 导出/导入功能带走（`src-tauri/src/api/sync.rs`）。

这把 ② 从"设计破坏性迁移 + 从 `order_items` 反推历史流水 + 处理负价格折扣行的语义归类"
降级为近乎 greenfield 的 schema 设计，工作量与风险各降一个量级。

**但"清零"必须是用户知情的选择，不是事故**，因为：

- `.boothpack` 只含 `master_products` + 图片，**不含展会、订单、销售流水**——用户唯一能主动做的
  备份，覆盖不了最有业务价值的数据
- 数据在 `app_data_dir/sale_system.db`（`src-tauri/src/db/mod.rs:21`），**没有便携模式**，
  普通摊主找不到路径手工备份
- 现有代码**没有任何自动备份**：`init_db` 跑 `migrate!()` 前不做快照；`reset_database`
  （`src-tauri/src/db/mod.rs:81-103`）直接 `remove_file`

因此：

**② 必须包含**：

1. 升级时把老库**改名留存**为 `sale_system.db.v1-backup`（不删）
2. 首次启动的迁移提示页提供"导出历史销售 Excel"——接现有 `src-tauri/src/api/stats.rs` 的导出逻辑到老库即可

**① 必须包含**：通用的"迁移前自动快照 + 失败回滚"基础设施（`init_db` 在跑 `migrate!()` 前先落一份快照）。
D1 之前这是 ② 的卡脖子前置条件；D1 之后它降级为常规保险丝，但仍必须有——因为 ② 之后的每一次
schema 变更都要靠它兜底。

### D2 — 复式范围：货 + 钱都双边

- **商品账户**：供货 / 现场仓 / 顾客仓 / 损耗 / 赠品
- **资金账户**：摊主自有 / 各渠道实收 / 社团往来 / 结算调整 / 对账差异
  （**已修正**：原写「应收」，见 ② spec 第 5.1 节——应收科目已取消）

每笔分录借贷必平，**写成不变量断言直接进测试**。

已知后果，接受：

- **结算时必须录收款渠道**，否则钱那条腿没有对手账户。摊主端本来就要人工点"确认收款"，
  把渠道选择并进那一步，不增加操作次数。
- ~~**"应收 vs 实收"成为真概念**：订单完成 = 记应收；摊主确认到账 = 应收 → 渠道账户。~~
  **此条已被 ② spec 第 5.1 节推翻。** 现场是一手交钱一手交货——摊主看到到账提示才点完成，
  **完成订单就是确认收款，是一个动作**。「应收」在正常流程里从不留余额，是两步模型的产物，
  已取消。应收与实收的差异只在**收摊对账时出现一次**（对着账单和现金盒核）。
  `docs/guide/workflow.md` 那句黑体警告仍然成立且更需要强调——完成订单是记账动作，不是收款动作。
- **赠品、损耗、样品、盘亏盘盈自然各有位置**（现在全是零实现）：赠品 = 货出账但钱不入账，
  损耗 = 货进损耗账户，盘点 = 一笔盘亏/盘盈调整分录。

取代现状：`products.current_stock` 是唯一状态源，**没有任何流水表**，库存变更有三套互不共享的实现——
下单扣减 `src-tauri/src/api/order.rs:130`（事务内，CAS `WHERE current_stock >= ?`）、
取消退回 `src-tauri/src/api/order.rs:451`（事务内，**独立重写的一套**，不是扣减的逆函数）、
管理员改初始库存 `src-tauri/src/api/product.rs:230`（**不在事务里**，差值调整）。
新模型下 `current_stock` 降为可从流水重算的缓存。

### D3 — 统一 Lot 售卖单元

一切卖出去的东西都是"套装（Lot）"，**单品是成分只有自己、数量为 1 的套装**。
定价与记账只有一条代码路径：

```
Lot → 展开成分 → 每个成分一条货的分录
Lot 价 → 钱的分录 + （Lot 价 − 成分原价合计）→ 一条折让分录
```

没有"单品走 A 路径、套装走 B 路径"的分叉——那正是现在三套库存逻辑的病根，不该在新模型里复发。

两个必须在 ② 的设计里处理掉的副作用：

- **size-1 套装不能让用户看见。** 管理员眼里仍然是"改这个商品的价格"，不能变成
  "改这个只有一件商品的套装的价格"。隐式派生或物理存在但 UI 层完全不露头，② 给具体方案。
- **顾客端价格必须可解释。** 自助点单场景下顾客看到总价被优化过却不知道为什么会不信任。
  购物车须明写"已应用：XX 套装 −10 元"，而不是默默给个低价。

### D4 — 折扣：最优解求解器 + 灵活空间

购物车端一键最优折扣：给定购物车与可用 Lot 集合，求把商品分配进 Lot 的最优解
（本质是加权集合覆盖）。摊位规模下（SKU 几十、购物车十几件、Lot 十几个）
暴力搜索加记忆化足够，性能不是问题。摊主可推翻求解结果（拆掉某个 Lot、叠一笔手工折让）。

手工折让仍然存在，但变成 `entry_type = 'discount'` 的正经分录——不挂商品、不动库存。

**取代现状的"负价格假商品"**：这是当前的官方方案，写在帮助文档里
（`frontend/src/views/Help.vue:334`："创建一个名为'优惠/抹零'的商品，价格设为 -5 元"），
`frontend/src/views/AdminEventProducts.vue:281` 还专门注释"价格可以为负数（对应折扣），这里无需验证"。
三个毛病：污染销量统计（`src-tauri/src/api/stats.rs` 把它当正常 SKU 汇总）、数据层分不清真商品与折扣、完全手动。

**求解器是纯函数**——不碰数据库、不碰 Tauri、不碰网络。它与"借贷必平"不变量一起，
构成 ① 的测试脚手架最高价值的两个靶子，而不是为了测而测。

### D5 — 契约：utoipa → OpenAPI → 生成 TS client

先 ③a 把 48 个 route（vision 关闭时 32 个） 的响应与错误收口成具名类型，再加 utoipa 注解生成 `openapi.json`，
用 openapi-typescript 出带路径与方法的完整 TS client。

**`openapi.json` 进 CI 做契约快照 diff**——契约变更在 code review 的 diff 里显形，而不是等运行时炸。

取代现状：50 个 `api.xxx()` 调用点，路径字符串与字段名全手写，JS 变量 camelCase / 接口字段 snake_case
两边不转换直接混用（如 `frontend/src/stores/productStore.js:141` 的 `{ is_active: newStatus }`）。
后端改个字段名前端不报错，只运行时静默出错，而且有 13 处 `catch {}` 直接吞掉。
唯一有契约注释的是 `frontend/src/services/vision.js` 的 JSDoc。

### D6 — 前端 TS：全量迁移

44 个 `.vue` 全改 `lang="ts"`，24 个 `.js` 全改 `.ts`，strict 开着，`vue-tsc --noEmit` 进 CI gate。

理由：大文件里 47~56% 是 CSS，真正的脚本层比看上去小很多；且半迁移的项目最难受——
类型在 TS/JS 边界上反复断裂，D5 生成的 client 的价值会被消掉一半。

### D7 — 外观：视觉方向不动

`frontend/src/config/theme.js` 的 token **值**原样保留，只在它上面建组件层。三件事：

1. **组件层收口** —— 当前每页各自重写一遍卡片/网格/弹窗/空状态的 scoped CSS：
   `frontend/src/views/CustomerView.vue` 1045 行里 506 行是 style（48%）、
   `frontend/src/views/AdminEventStat.vue` 56%、`frontend/src/views/AdminEventProducts.vue` 56%、
   `frontend/src/components/shared/VisionSearch.vue` 47%。
   **大文件的膨胀几乎全是 CSS，不是业务逻辑复杂。**
2. **信息架构重设计** —— 页面划分、导航、操作流。需容纳 ② 引入的新概念（见执行顺序第 2 条依赖）。
3. **移动端** —— 顾客端与摊主端都是手机/平板浏览器。现有 32 处 `@media` + 5 处 JS 断点判断说明
   适配做了，但做得不够好。

### D8 — vision 模块不动

`#[cfg(feature = "vision")]` 隔离的独立子系统（`src-tauri/src/vision/` 约 2100 行 + `src-tauri/src/api/vision.rs` 847 行），
靠 `master_product_images` / `image_embeddings` / `vision_index_meta` 三张独立表挂 `master_products`，
**完全不进交易路径**。1.2 对它只做两件事：跟着 ③a 做 handler 类型化、把 847 行的 `api/vision.rs` 拆开。

重做它只增加风险，不带来本次四个方向的任何收益。

## 1.2 明确不做（YAGNI）

- **App 前端 i18n** —— 当前零国际化，文案全硬编码中文。`docs/en` 和 `docs/ja` 是文档站翻译，
  与 App 无关，容易造成"这个项目做了国际化"的错觉。与本次四个方向都不沾边。

## 不能破坏的三件事

1. **离线局域网这条核心链路。** `docs/guide/philosophy.md`、`why-offline.md`、`boundary.md`
   三篇反复强调"不依赖公网、不依赖中心服务器"是这个产品区别于所有云端 SaaS 收银系统的根本卖点。
   v1.1.0 拍照识别在 LAN HTTP 下不可用的教训说明：任何新特性一旦要求联网前提或破坏
   "现场零网络可用"，会直接反噬产品最核心的信任基础。

2. **签名材料的连续性。** `my-release-key.jks`（Android 签名，指纹 `3228779e…86f2dcc4`）和
   `src-tauri/updater-key.key`（桌面 updater 私钥，key ID `C56CE43C94863207`）任一丢失或更换，
   都会让 v1.1.1 的线上用户要么被迫卸载重装、要么"检查更新"永久失效。1.2 无论怎么改架构都不触碰这两把密钥。

3. **支付非闭环的诚实披露。** `docs/guide/workflow.md` 顶部黑体强调"App 里面的'订单已完成'
   仅代表记录了一笔账，不代表钱真的到了你的账户"。D2 引入资金账户后，这句话依然成立且更需要强调——
   「完成订单」这个动作同时记了钱的移动，但那是**摊主声明收到了**，不是系统验证了到账。
   **不得让复式记账制造出"钱已到账"的错觉。**

## 附录三：②-3 执行后的状态（2026-09-24）

②-3（展会闭环与结算）已完成，`1.2-dev` 上本轮 **35 个提交**。

### 现在能做什么

**展会终于有终点了。** ②-1 建了账本、②-2 建了定价，但货只能进不能出；现在这一圈合上了。

- **收摊向导**（摊主端）：清点订单 → 盘点 → 带回 → 结算，四步。
  清 pending 是硬阻断（那些订单的货在顾客仓、钱一分没收）；盘点可跳过但会留痕；
  带回是一键；结算要求现场仓全部归零。**在第几步由后端状态推出来**，退出重进不丢进度。
- **退货**（摊主端）：按订单行逐行退、可退部分数量，退给顾客按 `paid`、冲销货主按 `allocated`，
  顾客没拿回的部分归**货主**。退款渠道可与收款不同。
- **赠送与报废**（摊主端）：货从现场仓挪进虚拟仓，钱默认不动；「摊主自掏」是可选开关。
- **垫付与结算调整**（管理端）：各自入账，删除走冲正。**展会结算之后仍然可以增删。**
- **结算单**（管理端）：每货主一块（货的六项去向 + 钱的六项加减 + 我应转给），
  跨货主的收摊清点，四 sheet 的 xlsx 导出。页面和导出渲染**同一个 `SettlementReport`**。
- **冻结**：`已结算` 之后只有垫付、结算调整、收摊清点三件事还能写；
  展会状态不能绕过收摊流程直接设成已结算，也不能解冻。

  而盘点那一屏是逐行输入的表格，且本轮刚改成不预填。这是移动端那一批里优先级最高的一处。
- **结算单开不开给摊主角色**（见上面 spec §9 那条）。
- 本轮新建的六个前端页面/组件都按现有模式做、没有视觉投入，等 ④ 统一收口。
- `components/vendor/` 下现在有三种弹窗写法并存；xlsx 导出用 `alert()` 而同页其余用 toast。

### 留给 ③b 的

- **`SettlementReport` 是最值得先上 utoipa 的类型**：嵌套三层、十几个 `Money` 字段、前后端共享，
  而前端现在是手写解构，字段名错了不报错、只在页面上显示 undefined。
- **`Money` 在 JSON 里是裸整数分**，TS 侧会生成成 `number`，和件数、id 没有类型区别。
  需要 branded type，否则「把分当成元显示」TS 也拦不住。
- **冻结例外的三个端点是 API 契约的一部分**，不是实现细节，要写进 OpenAPI 的描述。

### 下一步

按路线图是 **③b**（utoipa → `openapi.json` → 生成 TS client → 前端 TS 全量迁移），之后是 ④。

### 真机验过的 / 没验过的

**全部没验。** 本轮在 Linux 开发机上完成，门禁全绿，但传输层（原生 fetch / plugin-http 切换）、

5. LAN 顾客端下单 + 摊主端 3 秒轮询

### ③b 暴露的、值得记住的

- **跨模型执行的最大收益又一次是「发现计划本身错了」。** store 批次的 4 个 worker 里有 3 个
  **各自独立**报告了同样两处 client 类型缺陷（openapi-fetch 的 `Readable<T>` 会把 branded
  `Cents` 映射坏；`unwrap` 推断出 `T | undefined`），并在调用点加了约 20 处带说明的
  `@ts-expect-error` 绕过——这正是 brief 要求的做法。修在 client 层一次之后，绕过全部删掉。
- **门禁脚本会静默空转，而且发生了三次。** 路由改成 `routes!` 之后守卫门禁找不到写 handler；
  `method(post, put)` 又让它漏掉 3 个；最后我自己写的本地门禁脚本用 `(cmd) && echo ok`，
  `set -e` 不管 `&&` 列表里的失败，放过了一次 clippy 错误。前两次的修法是加**交叉校验**：
  `openapi.json` 里的每个写操作，守卫脚本都必须认得出来。
- **新的形状测试逼出了一个真 bug。** 销售汇总导出写系统临时目录下的固定文件名，同一场展会
  两个下载并发时一个删了另一个正要读的文件 → 500。测试并行时偶发，现实中是两台设备同时导出。
- **「形状清理」清单（77 条）几乎都不是形状问题。** 大部分是纯文本错误体、吞错误、f64 元金额，
  改它们都是行为变化。③b 只做了「值域固定的字符串声明为枚举」一类（线上 JSON 不变），
  其余留在 `docs/superpowers/specs/2026-09-24-shape-cleanups.md` 作为 ④ 与后续的输入。

### 留给 ④ 的（本轮新增）

- **错误体统一**要和**文案重写**一起做：现在前端对纯文本错误体显示的是调用方的中文兜底文案；
  直接改成 `{"error": "Database Error"}` 会让用户看到英文。见 shape-cleanups 的 A 类。
- **吞错误**（B 类）改掉之后会出现新的 500/404，需要前端的错误态设计配合。
- `MasterProduct.default_price` 与 legacy 数据仍是 f64 **元**（C 类），改分牵涉 `.boothpack` 跨版本兼容。
- `EditEventForm` 读取 `vendor_password`，但 `EventResponse` 里没有这个字段（运行时恒为空，
  恰好等于「留空不改」）；路由的 `id` 是字符串、到 store 才 `Number()`。
- `types/openapi-typescript-helpers.d.ts` 是第三方类型的修补副本；升级 openapi-fetch 时
  `core.spec.ts` 会提醒重新打补丁。
